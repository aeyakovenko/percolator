# The engine's unchecked arithmetic in the deployed build (engine 71076137, program b5731c7a)

Generated by `wrap_census.py`. Cargo applies only the root manifest's profiles, so the program's manifest decides how the engine is compiled into the deployed program. Since program `cd8a446a` its release profile checks the program's own arithmetic (an overflow aborts the transaction) and leaves every dependency, the engine included, unchecked (`[profile.release.package."*"] overflow-checks = false`): with the engine checked, the 14-leg atomic exit of INV-073 exceeds the 1.4M CU limit. Before that commit no crate was checked.

Every proof of this ledger was made with overflow checks on: Kani always checks, and the Aristotle specs said so. With checks on, an overflowing operation stops the call; in the deployed engine it continues with a wrapped value. So a no-panic proof also rules out wrapping and carries to the deployed build, but a statement of the form "if the call returns, then ..." carries only where the operations it runs cannot overflow. The pieces below are those obligations: one per deployed engine function with an unchecked `+`, `-`, `*`, shift or negation that no proved no-panic piece of the function itself covers.

**Count.** 236 such operations in 121 deployed functions of `src/v16.rs`; 44 of them in 23 kernels whose no-panic piece is proved or verified; **192 in 98 functions are pieces of the ledger (PO.*)**, open until a proof closes them (the ledger has each one's status). Not counted: 26 divisions and remainders (checked in every build, so the proofs' model and the deployed build agree on them), 0 operations outside deployed functions, and `src/wide_math.rs` (the arithmetic layer proved the exact panic condition of each of its functions; the P pieces state that no call from `src/v16.rs` meets it).

Clippy ran on the host build. The engine has no target-specific code (`target_os` appears nowhere in `src/v16.rs`), so it saw every function the deployed build compiles.

3 operations span more than one line; clippy's text was cut, so they are listed with operator `?` and counted (lines 3464, 3692, 3823).

**How a piece closes.** A no-panic proof of the function for the inputs its deployed callers can pass (Kani, or Aristotle with overflow checks on), or a caller's no-panic proof that covers every call, or replacing the operation with checked arithmetic that returns an error (a code change: it costs compute on paths near the limit). Many are loop counters bounded by a slice length or differences guarded by a comparison just before them; the proof still has to say so.

**What is already proved and depends on this.** A proved "if it returns" statement about a function carries to the deployed build when the no-panic pieces it needs are done. `make_ledger.py` checks that for every proved piece at each generation and lists the exceptions in the ledger ("Which proved pieces carry to the deployed build").

**The program.** Its own arithmetic is checked in the deployed build: an overflow aborts the transaction, which no safety statement has to exclude. A liveness statement (an instruction that must succeed) has to show it does not happen, as it shows for every other error.
