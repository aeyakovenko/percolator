# Feasibility trial: `processor::handle_deposit` (percolator-prog eb9807c5, engine 4e77481b)

## Step 1: feasibility report

### Can the crate and its dependencies be taken?

Yes. `handle_deposit` and every function it calls are taken from their source, with no source
changes. That includes the engine, `spl-token` 4.0.0, `solana-program` 1.18.26, `bytemuck`, and the
standard library's `Rc` and `RefCell`. The configuration is the deployed one:

- release profile as uploaded, so no overflow checks and no debug assertions;
- default feature `no-entrypoint`;
- no `cfg(kani)`, no test code.

**Target.** Results are about the same source compiled for x86-64 Linux, not for SBF. The differences
that could matter:

- **`solana-program` functions with `cfg(target_os = "solana")` bodies.** These are
  `Pubkey::find_program_address`/`create_program_address`, `invoke_signed`, `Clock::get`,
  `AccountInfo::realloc` and `AccountInfo::data_len`. All of them are among the assumed functions
  below, so their host bodies are not relied on.
- **Alignment of `u128`** (16 on x86-64, 8 on SBF). The account structures the handler reads all have
  alignment 1, for example `PortfolioAccountV16Account` (9,419 bytes) and `MarketGroupV16HeaderAccount`
  (710 bytes). So field offsets and the `bytemuck` casts over account bytes are the same on both targets.

The program's reached code has no target-dependent bodies. Its `cfg(not(target_os = "solana"))`
items are host-only extras that `handle_deposit` does not reach.

### Why W1 costs about as much as W3

Every Rust result here has the form: "on every run there is no undefined behaviour, and *if* the handler
returns `Ok`, P holds."

W1's P is settled by the first checks, which take 15 of the handler's 69 source lines. The "no
undefined behaviour" part still covers every path after those checks, on adversarial accounts and
arguments. That means:

- the 34 `?` exits of `handle_deposit`, each of which must release the live `Ref`/`RefMut`
  guards (four `RefCell` borrows in all);
- `read_market_config_mode_and_capacity`, with the wrapper-config validation closures and the engine
  config validation;
- the two views and `PortfolioV16View::validate_with_market`;
- `deposit_not_atomic`, which runs `validate_with_market` twice and `validate_shape`, including the
  engine's U256/U512 arithmetic;
- token-account decoding;
- the PDA derivations;
- `transfer_tokens`.

All of these are your own code. They have to be proved, either from their bodies or as proved
contracts, not assumed. So W1 needs essentially the whole memory-safety proof of the handler. W2 and
W3 add functional facts on top.

## Overflow checks

The uploaded build wraps on overflow. W1, W2 and W3 are all "if `Ok`" properties. Turning overflow
checks on only adds panics at operations that would overflow. So every run that returns `Ok` with
checks is also a run that returns `Ok` without checks, with the same effects. A proof under wrapping
therefore carries over to the checked build; the converse does not.

The places where the two builds differ are the wrapping `+`, `-` and `*` in reached functions of the
program and engine. Examples:

- `state::market_slot_capacity`, `state::validate_market_dynamic_len`;
- `state::read_u16`/`read_u64`, `state::write_portfolio_matcher_sequence`, `state::market_header`;
- `PortfolioV16View::validate_with_market`, `validate_source_credit_shape_with_market`;
- `PortfolioV16ViewMut::compact_source_domains`;
- `TokenValueFlowProofV16::validate`;
- `V16Config::validate_solvency_envelope_range`;
- the `wide_math` U256/U512 routines.

With checks on, each of these can panic instead of wrapping. Under wrapping, a proof must also show
that a wrapped value never lets a check pass that should have failed.

## Suggestion for cutting the 56 instruction-level properties

Prove reusable contracts once for:

- the account checks;
- `read_market_config_mode_and_capacity`;
- the two views;
- the token verifiers;
- `transfer_tokens`;
- the sequence-binding helpers;
- each engine entry point a handler calls.

Then state each instruction property as a composition over those contracts. A property stated directly
on a handler, however small its conclusion, pays the whole safety cost of that handler.
